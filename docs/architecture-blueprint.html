TAKAFLOW Architecture Blueprint

A system that keeps recyclable-material inventory correct when it's recorded on devices that lose connectivity for hours and reconcile later. That correctness problem — not the number of screens — is the technical core of this project; everything else (portals, matching, reporting) is business context around it.

Prepared for Final-Year CS Project Status Reframed after review — see §25 for resolved decisions Real timeline 2 weeks total (1 build, 1 test) — drives the MVP in §22 Core scope Offline-safe collection recording + ledger · thin admin view
§01

Executive Summary

Reframed thesis (post-review)

Early feedback on this project was blunt and fair: as a list of features — registration forms, portals, a marketing site — this reads like a business idea, something a non-technical founder could commission from any agency. That critique lands on the parts of the brief that are ordinary CRUD. It doesn't land on the one requirement that ordinary CRUD cannot satisfy: recording collections on a device that may be offline for hours, then reconciling those records into a shared inventory count without ever double-counting, losing an entry, or letting it go negative. That is a real correctness problem under concurrency and unreliable connectivity, and it is the thing this project is actually about. Every section below still designs the full system honestly, but §22 now organizes priorities around that thesis explicitly, and the defense narrative should lead with it, not with the interface count.

TAKAFLOW is architecturally sound as proposed, with one caveat that matters more than any technology choice: the scope, as written, is closer to a small startup's first product than a two-week build. Four distinct interfaces, offline-first sync, a matching engine, and a forecasting pipeline are each individually reasonable. Attempted together, in the time actually available, they are not. This document designs the full system honestly — because a good architecture has to account for everything the system will eventually need — and then draws a hard, explicit line in §22 between what ships now and what is documented as future work. That line is the single most important decision in this blueprint.

The proposed technology stack (React/TypeScript/Vite/Tailwind, FastAPI, PostgreSQL/SQLAlchemy, PWA/IndexedDB, scikit-learn) is kept almost entirely as-is. It is a competent, defensible, well-documented stack for exactly this kind of system, and changing it for the sake of using something more fashionable would be bad engineering. The changes recommended are narrow: a data-access library on top of raw IndexedDB, an explicit event-sourced inventory ledger instead of a single mutable counter, and a monorepo with shared packages instead of four unrelated codebases.

The database, as sketched in the brief, would work for a demo but would silently corrupt itself under real concurrent use — specifically around inventory counting and purchase-rate history. §8–§11 redesign those parts. Everything else in the brief's starting schema is a reasonable first draft that this document refines rather than replaces.

§02

Requirements Analysis

Before designing anything, it's worth separating what the brief actually requires from what it merely illustrates. Three principles run through the whole document and should be treated as load-bearing:

  1. Centralization — one backend, one database, one identity system, regardless of how many frontends exist.
  2. Offline-first collection recording — the collection-point app must function as a local-first application with eventual consistency, not a thin client that happens to cache a bit.
  3. Predictive analytics as the only "intelligence" — explicitly not computer vision, IoT, or blockchain. This is a helpful constraint: it keeps the ML component honest and scoped to tabular time-series forecasting on operational data that already exists.

The brief also states several things as illustrative ("possible starting fields", "example endpoint groups", "a possible sequence") rather than fixed requirements, and explicitly invites disagreement. This document exercises that invitation throughout — each major section either adopts, adapts, or explicitly rejects the starting suggestion, with reasoning.

Implicit assumption · Confirmed (§25 item 3)

The brief assumes collection points are fixed physical premises with intermittent but eventually-restored connectivity (a branch office, not a person walking around with a phone and no signal for days). This assumption drives the offline-sync design in §10. Confirmed: collection is branch-based, not field-agent-based, so the desktop/tablet storage-quota and background-sync assumptions in §10 stand as designed.

§03

High-Level Architecture

TAKAFLOW is a single centralized system exposed through multiple purpose-built clients. There is one FastAPI service, one PostgreSQL database, and one authentication domain. The four interfaces are different presentations of the same backend, not four separate products that happen to share a name.

  • Public Website — mostly static/server-rendered marketing content, reading a small amount of public data (collection points, materials, impact stats) from the API. No authentication.
  • Collection-Point PWA — an installable, offline-capable single-page app used by branch staff. Authenticated. Writes flow through a local-first sync engine before reaching the backend.
  • Admin Portal — a standard authenticated SPA for management, configuration, and analytics. No offline requirement.
  • Buyer Portal — a standard authenticated SPA for industrial buyers. No offline requirement.

A single ML/analytics component runs out-of-band from the request/response cycle: a scheduled batch job reads from PostgreSQL, trains/refreshes forecasting models, and writes predictions back into the same database, where the API simply reads them like any other table. The model does not run inline on user requests — this keeps the web tier simple and the ML tier independently testable.

§06

User Roles & Permissions

Three roles are sufficient for this system's actual complexity. A full many-to-many ROLE/PERMISSION schema (as real RBAC systems use) would be over-engineering for three roles with stable responsibilities — it's designed for organizations that invent new roles at runtime, which TAKAFLOW does not need. Enforce permissions in a small, explicit policy table in code, backed by a single role enum column on USER. The schema stays extensible (see §25) if that ever changes.

§08

Database Architecture

The brief's starting entities are a good sketch. Three structural gaps would cause real problems if built as-is, and are corrected here before anything else:

Challenge 1 — a single mutable quantity_available is not enough

Directly incrementing/decrementing one column from multiple concurrent writers (collections arriving, transfers going out, offline sync catching up hours later) is exactly the pattern that produces double-counting and negative inventory under concurrency — the two failure modes the brief explicitly wants avoided. §11 replaces this with an append-only inventory ledger plus a derived summary row, which is both safer and auditable — an examiner will ask how you know your inventory numbers are correct, and "we have a ledger" is a real answer.

Challenge 2 — purchase rate cannot be a single field on MATERIAL

The brief lists purchase_rate as a field directly on MATERIAL. But a transaction must record the rate that was actually applied at that moment, at that branch — and rates change over time and plausibly differ by branch. A single mutable field loses history the instant it's overwritten. This is replaced with a MATERIAL_RATE history table below.

Challenge 3 — "materials accepted per collection point" needs its own table

The public site must show "materials accepted at each collection point" (§1) and rates can vary by branch. Both require a many-to-many join between COLLECTION_POINT and MATERIAL, which isn't in the brief's starting list.

Key constraints worth stating explicitly

  • collection_transaction.client_transaction_uuid — UNIQUE, NOT NULL. This single constraint is what makes offline sync idempotent (§10).
  • inventory_summary — unique on (collection_point_id, material_id); CHECK (quantity_on_hand >= 0) and CHECK (quantity_reserved >= 0).
  • collection_point_material — unique on (collection_point_id, material_id).
  • material_rate — for a given (material_id, collection_point_id), at most one row with effective_to IS NULL (open-ended/current rate) enforced by a partial unique index.
Change — no supplier registration or identity (§25 item 7)

Confirmed: collectors are not registered and do not need to be identifiable across visits — anyone, including someone with no phone or ID, can bring material, have it graded and weighed by staff, and be paid on the spot. There is therefore no supplier entity, no identifier-uniqueness constraint to satisfy, and no registration/search screen. collector_name and collector_phone become plain nullable text fields on collection_transaction — captured for the payment/dispute record only, never deduplicated or used to build a persistent identity. If repeat-supplier tracking or self-service accounts become worth doing later, that reintroduces a proper supplier entity as a schema migration, not a redesign — nothing here blocks it.

§10

Offline-First Architecture

Stack decision: PWA + IndexedDB is kept, but not raw IndexedDB — wrap it with Dexie.js. Raw IndexedDB's callback/cursor API is exactly the kind of hand-rolled complexity that turns into unmaintainable code in a student project; Dexie gives promise-based queries and versioned schema migrations over the same browser API, at negligible cost.

Data model on-device

  • outbox store — one row per not-yet-confirmed transaction: { client_transaction_uuid, payload, status, attempts, last_error, created_at }.
  • reference cache — read-only mirror of materials, rates, and the employee's own collection point, refreshed opportunistically whenever online, so the form works fully offline.
  • local history — recently synced transactions, cached for the "today's collections" view without a network round trip.

Lifecycle

Answers to the brief's specific scenarios

ScenarioBehavior
Browser/tab closed with pending recordsIndexedDB is durable storage; nothing is lost. navigator.storage.persist() is requested on first login to reduce eviction risk under storage pressure.

Same transaction submitted twice (double-tap, retry after timeout)The client-generated UUID is the idempotency key. The server has a UNIQUE constraint on it; a duplicate insert is caught and answered with the original record's server ID as a 200, not an error — the client treats this as success.

Retry strategyExponential backoff (5s, 15s, 60s, capped at 5 min) per record, independent per record so one bad record doesn't block others.

What "conflict" actually means here

Because collection transactions are creates, not edits, there is no field-level merge conflict to resolve — the brief's classic "two users edited the same row" scenario doesn't apply. The real conflict case is stale reference data: an employee selects a material or rate while offline, and by the time the record syncs hours later, an admin has deactivated that material or superseded that rate. The server rejects with a distinguishable CONFLICT reason, the record is flagged for the branch supervisor to review (never silently dropped or silently auto-corrected), and it's resolved by picking the correct current material/rate and resubmitting — a human decision, not an automatic merge.

Demo plan · Confirmed

The correctness demo (§01, §26) is done practically live, not narrated or scripted around devtools throttling: on the actual device, switch it to airplane mode, record 2–3 collections while offline (shown queued in the outbox UI), attempt a duplicate submit to show the idempotency key catch it, re-enable connectivity, and watch the queue drain and the admin view's inventory update to the correct total. No special "chaos mode" feature is needed for this — it exercises the real online/offline browser events and sync engine described above, so the only extra work is making sure those states are visibly surfaced in the collection-app UI (a small outbox/sync-status indicator) and rehearsing the script.

Architect's note — storage limits

Confirm the assumption from §02: this design assumes desktop/tablet browsers at a fixed branch, where IndexedDB quotas (typically hundreds of MB to a few GB depending on browser/OS) are a non-issue for text-sized transaction records. If field staff on budget Android phones turn out to be in scope, storage-eviction behavior on mobile Chrome/Safari needs a second look before this is finalized.

§11

Inventory Architecture

Recommended model: an append-only ledger is the source of truth; a summary table is a fast, transactionally-updated read cache of it. This is the single highest-leverage change in this whole document relative to the brief's starting design, because it directly targets every failure mode called out in §8 of the brief (double counting, negative inventory, duplicate updates, race conditions, offline-sync incorrectness) with one consistent mechanism instead of ad-hoc guards.

inventory_ledger (append-only)

{ id, collection_point_id, material_id, movement_type, quantity_delta, reference_type, reference_id, created_at } — movement_type ∈ COLLECTION (+), TRANSFER_OUT (−), RESERVATION (moves on-hand→reserved, net zero on-hand), RESERVATION_RELEASE (reverse of above), ADJUSTMENT (admin correction, requires a reason and is itself audit-logged).

inventory_summary (derived)

{ collection_point_id, material_id, quantity_on_hand, quantity_reserved, updated_at }, unique on the first two columns. Every write to the ledger and the corresponding update to the summary happen inside the same database transaction, using an atomic UPDATE ... SET quantity_on_hand = quantity_on_hand + :delta (never a read-then-write in application code), with a CHECK constraint preventing the balance from going negative. This is a simple, well-understood pattern (not full event-sourcing with state rebuilding) — appropriate for this scale, and it directly satisfies "avoid negative inventory" and "avoid race conditions" without needing application-level locking.

Why not just SELECT ... FOR UPDATE with read-modify-write?

That also works and is a legitimate alternative, but an atomic single-statement increment is simpler to reason about, needs no explicit lock management, and is what the ledger pattern naturally produces. SELECT FOR UPDATE is mentioned here only as the fallback if a future movement type needs multi-row conditional logic that can't be expressed as one atomic increment.

Reservation flow for buyer fulfillment

When a transfer is proposed against a buyer request (§12), the system inserts a RESERVATION ledger entry, moving quantity from on-hand into reserved before physical dispatch — so two buyer requests can never both believe the same stock is available. If the transfer is cancelled before dispatch, a RESERVATION_RELEASE entry reverses it. On actual dispatch, a TRANSFER_OUT entry removes it from reserved permanently. Collections increase quantity_on_hand directly and never touch quantity_reserved.

Offline-synced collections post to the ledger at sync time (not at the moment the employee typed it), which is correct: the physical material didn't exist in the branch's countable inventory until it was actually verified and recorded, and using the sync timestamp (with the original transaction timestamp preserved separately for reporting) avoids inventory ever moving backward when a batch of offline records lands.

§12

Buyer Request & Matching Architecture

The brief's status list is good with one addition: an EXPIRED state for requests whose required_date passes without fulfillment, so stale requests don't sit in SUBMITTED forever. Final lifecycle: SUBMITTED → UNDER_REVIEW → PARTIALLY_FULFILLED → FULFILLED, with CANCELLED and EXPIRED as terminal exits from any non-final state.

Matching logic — deliberately simple

The brief explicitly warns against unnecessary optimization complexity, which is the right call here: this is not a vehicle-routing problem. The matching service, when asked to evaluate a request, does the following, in order:

  1. Query inventory_summary for the requested material across all collection points, filtered to points with available (on-hand minus reserved) stock > 0.
  2. Rank candidate points by same-county match to preferred_location first, then by available quantity descending.
  3. Greedily allocate from the top of that ranked list until the requested quantity is covered or supply is exhausted — this is the entire "algorithm": a sort and a running-total loop, not a solver.
  4. If supply is exhausted before the request is covered, query the prediction table for the shortfall's remaining quantity, clearly labeled as a separate, non-guaranteed number (see below).

Crucially, matching proposes an allocation; it does not automatically create transfers or reservations. Admin/staff review and confirm before any RESERVATION ledger entry is created — a human-in-the-loop step that removes the need for the algorithm to handle every edge case autonomously, and matches the brief's instruction to keep this realistic.

Actual vs. predicted — enforced, not just displayed

Non-negotiable design rule

"Current available inventory" and "predicted additional availability" must never be summed into a single number returned by the same field. The API returns them as two distinct, separately-labeled values (current_available_kg and predicted_available_kg with the prediction's confidence interval), and the buyer-portal UI renders them in visually distinct blocks — never as one merged total. This is a contract enforced at the schema level (two separate response fields), not just a UI convention that could be silently violated later.

§13

Predictive Analytics Architecture

Pipeline

flowchart LR
    A["collection_transaction\n(synced, real data only)"] --> B["Aggregate to\nweekly buckets per\n(collection_point, material)"]
    B --> C["Feature engineering:\nlags, rolling means,\nweek-of-year, trend"]
    C --> D{"Enough history?\n(>= ~12 weeks)"}
    D -- no --> E["Fallback: naive /\nmoving-average baseline\nflag as low-confidence"]
    D -- yes --> F["Train & time-based\nholdout split"]
    F --> G["Compare: seasonal-naive,\nLinear Regression,\nRandom Forest, Gradient Boosting"]
    G --> H["Select best by MAE/RMSE\non holdout"]
    H --> I["Write to prediction table:\nvalue, interval, model_used,\nmae, generated_at"]
    E --> I
    I --> J["Admin dashboard /\nBuyer portal (labeled 'predicted')"]
  • Training data comes only from real, synced collection_transaction rows — never from seed/demo data. Any demo data used during development is generated with an explicit is_demo_data flag and is excluded from training queries by default.
  • Validation split is chronological, not random — training on the past and testing on a later holdout window, because random splits leak future information into a time-series model and would produce misleadingly good metrics.
  • Model selection is empirical: a seasonal-naive/moving-average baseline is always trained alongside Linear Regression, Random Forest, and Gradient Boosting; whichever wins on MAE/RMSE for that specific (point, material) series is what gets used — there is no assumption that a fancier model wins by default, and for a thin dataset the baseline will often legitimately win.
  • Insufficient data (a new branch, a rarely-collected material) is handled by explicitly returning "insufficient historical data for a reliable forecast" rather than emitting a number with false confidence — this is a direct requirement from the brief and is enforced by a minimum-sample-size gate before any regression model is even attempted.
  • Uncertainty is reported as a simple interval (e.g., ±1 residual standard deviation from the holdout, or the empirical range across the compared models) — adequate for "roughly how much more might become available," which is the actual decision this number supports.
§14

API Architecture

REST, versioned under /api/v1/ from day one (near-zero cost now, avoids a painful migration later). Grouped by domain, matching §07's modules: /auth, /collection-points, /materials, /suppliers, /collections, /payments, /inventory, /buyers, /buyer-requests, /matching, /transfers, /predictions, /sync, /reports.

  • Auth: JWT access token (short-lived, ~15 min) + rotating refresh token stored hashed server-side so it can be revoked; every protected route depends on a FastAPI dependency that decodes the token and loads the current user's role and scope.
  • Authorization: a small per-route dependency (require_role("admin"), require_own_collection_point()) rather than checks scattered inside handler bodies.
  • Schemas: separate Pydantic models for request bodies, response bodies, and internal DB-facing shapes — never return an ORM object directly.
  • Validation: Pydantic field validation at the boundary (types, ranges, required fields); business-rule validation (e.g., "quantity can't exceed a sane branch-day maximum") lives in the service layer, not the schema.
  • Errors: a consistent JSON error envelope ({ "error": { "code", "message", "details" } }) and correct HTTP status codes — 422 for validation, 409 for conflicts (rate/material staleness, duplicate UUID under non-idempotent conditions), 403 for authorization failures.
  • Pagination/filtering/sorting: cursor or offset-based pagination (offset is fine at this scale) with consistent ?page=&page_size=&sort=&filter[...] conventions across every list endpoint.
  • Idempotency: the sync endpoint is idempotent by design via client_transaction_uuid (§10); other mutating endpoints accept an optional Idempotency-Key header for the same reason where double-submission is a realistic risk (payments).
  • Rate limiting: applied at the reverse-proxy layer on auth endpoints specifically, to blunt credential-stuffing attempts, per §18.
§15

Frontend Architecture

Decision: Option B — one monorepo, four separate applications, shared internal packages. Not Option A (one app with role-based sections): that would force offline/service-worker complexity onto the marketing site's bundle and force marketing/SEO concerns onto the authenticated apps, for no shared benefit — these four surfaces don't actually share screens, only components and types. Not Option C (separate repositories): for a project built and defended by one person (or a small team) on one timeline, splitting into separate repos multiplies CI/versioning overhead for zero real isolation benefit and makes keeping the shared API types in sync actively harder.

§16

Backend Architecture

Layered, one direction of dependency: routers → services → models, with a thin repository layer only where a service's queries are complex enough to be worth isolating (inventory, matching). Route handlers do request/response translation and permission checks only — they never contain business logic.

Cross-cutting concerns (auth, RBAC guards, request logging, error handling) are implemented as FastAPI dependencies and middleware, not duplicated per route. Alembic manages migrations; every schema change is a migration file, never a manual production edit.

§18

Security Architecture

  • Passwords: hashed with bcrypt/argon2 via passlib; never logged, never stored or transmitted in plaintext.
  • AuthN/AuthZ: JWT access + rotating refresh tokens (§14); role- and scope-based authorization enforced server-side on every route.
  • Input validation: Pydantic at the API boundary; parameterized queries exclusively via SQLAlchemy (no raw string-built SQL, eliminating injection risk by construction).
  • Secrets: environment variables loaded via .env in development (git-ignored) and the hosting platform's secret store in production — never committed, never hard-coded.
  • Rate limiting: applied to /auth/login and /auth/refresh specifically, to slow credential-stuffing.
  • Audit logging: two distinct trails — sync_log for offline-sync attempts (operational), and audit_log for admin actions on users, rates, and materials (accountability). Conflating these would make either one harder to query meaningfully.
  • Offline data at rest: IndexedDB is not encrypted by the browser and is accessible to anyone with access to the device/profile. For this project's threat model (staff-operated branch devices, not sensitive personal data beyond a supplier's name/phone), this is an accepted, explicitly documented risk rather than a solved one — full at-rest encryption of IndexedDB is real engineering effort disproportionate to what's stored there.
Explicitly not claimed as done

None of the above is implemented yet. This section describes what the architecture requires; §19–§20 describe how it will be verified once built.

§20

Deployment Strategy

Kept deliberately free-tier and simple, per the brief's instruction to avoid unnecessary paid services:

  • Development: Docker Compose running FastAPI + PostgreSQL locally; frontends via Vite dev servers.
  • Production/demo: Postgres on a managed free tier (e.g., Neon or Supabase), FastAPI on a small always-on-friendly host (e.g., Render/Railway free/hobby tier), static frontends on Netlify/Vercel/Cloudflare Pages. The collection-app PWA deploys the same way as any static SPA — the offline behavior is a client-side concern, not a hosting concern.
  • ML job: a scheduled task (cron on the same host, or the platform's built-in scheduled-job feature) rather than a separate always-on service — it runs briefly, on a schedule, and writes to the same database.
  • Maps: use Leaflet + OpenStreetMap tiles for collection-point maps on the public site, not the Google Maps API, to avoid a paid/keyed dependency for a feature that doesn't need it.

Development Roadmap

Real timeline note

The 15 phases below are the full system's roadmap, useful as a reference for sequencing and dependencies — but the actual build window is 2 weeks (1 for development, 1 for testing), not an academic term. In that window, realistically only Phases 1–8 (foundation through offline-first collection recording) plus a thin slice of Phase 9 are buildable and testable; see §22 for the resulting MVP. Phases 9–13 stay as documented future-state architecture unless time is left over.

Reordered from the brief in one meaningful way: authentication/RBAC and the inventory ledger are pulled forward, because every later module (collections, payments, matching) depends on both existing correctly first, and retrofitting the ledger pattern after collection transactions already exist would mean a data migration under time pressure.

Phase 2 — Database & migrations: full schema from §08, Alembic baseline. Depends on: 1.

Phase 4 — Collection points & materials: admin CRUD, per-point material acceptance, rate history. Depends on: 3.

Scheduling implication

Phase 13 (predictions) is structurally the last feature that can produce believable results, because it needs real weeks of Phase 6–8 data to train on. If the academic timeline is fixed, treat Phase 13 as the one most likely to be scoped down to "pipeline works correctly on the data available" rather than "forecasts are highly accurate" — and say so plainly in the final report rather than overselling it.

§22

MVP vs Future Scope

Reordered around the reframed thesis in §01: the point of this project is proving that inventory recorded offline stays correct under duplicate submits, dropped connections, and concurrent writes. Everything in the must-have list exists to build and demonstrate that; everything demoted to nice-to-have or future is a feature the brief wanted but that a business-in-a-box tool could also provide, so it isn't where the limited two-week budget should go.

Must-have (the actual 2-week build: 1 week dev, 1 week test)

  • The centerpiece: offline-first collection recording — Dexie outbox, client-UUID idempotency, retry/backoff, and the double-submit / drop-mid-sync / stale-reference-conflict scenarios not just handled but demonstrably tested (§10, §19)
  • The proof: append-only inventory ledger + derived summary, atomic writes, non-negative constraint — with a scripted or live "chaos" demo (kill connectivity, fire a duplicate, race two writes) showing the count stays right (§11)
  • Auth + RBAC — Admin and Collection-Point Staff only; Buyer login deferred with the buyer portal below
  • Materials & collection points — minimal config, no per-branch rate history nuance beyond what §8 already requires structurally
  • Collection transactions — walk-in, no registration (§25 item 7), with grade captured inline (§25 item 4)
  • Payments recorded manually — method (M-Pesa or cash) + reference number, no live disbursement (§25 item 2)
  • One thin admin view: today's collections + current inventory per branch, reading real data — enough to prove the ledger, not a full dashboard

Nice-to-have (only if the core above is solid with days to spare)

  • A simple rule-based low-stock flag computed off the ledger (no ML) — see §25 item 8
  • Minimal public site reading real collection-point/material data from the API
  • Buyer portal + simple matching against current inventory only (no predicted-availability blending)

Future scope (explicitly out of bounds for this build)

  • Predictive analytics of any form — no real usage history exists at this timeline to train or honestly evaluate a model against (§25 item 8)
  • A registered/persistent supplier entity, search, or self-service accounts — collection is walk-in only by design (§25 item 7)
  • Live M-Pesa/Daraja API disbursement integration (see §25 item 2)
  • Multi-branch matching & predicted-availability blending, inter-branch transfers
  • Map view (Leaflet) on public site
  • Any computer vision, IoT, blockchain, or hardware integration — excluded per the brief, not reconsidered here

§24

Architectural Decision Record

ADR-01 — Frontend architecture

Monorepo, 4 apps, shared packages
Reason
The four interfaces have genuinely different runtime requirements (offline vs. not, public vs. authenticated, SEO vs. app-shell) but share components, types, and an API client. Monorepo captures the sharing without forcing one bundle to carry every requirement.
Alternatives
Option A (one app, role-based sections) — rejected: bloats every client with concerns it doesn't need. Option C (separate repos) — rejected: multiplies process overhead for a single-team project with no isolation benefit.

ADR-02 — Backend architecture

Layered: router → service → model
Reason
Keeps business rules (inventory math, matching, idempotency) testable in isolation from HTTP and out of route handlers.
Alternatives
Logic-in-routes ("fat controllers") — rejected: untestable without spinning up HTTP, and the brief explicitly asks not to do this.

ADR-03 — Database engine & ORM

PostgreSQL + SQLAlchemy + Alembic, as proposed
Reason
Relational integrity (FKs, check constraints) is doing real work here — inventory correctness depends on it. Kept as originally proposed; no change needed.
Alternatives
None seriously considered — this is the right tool for this data shape.

ADR-04 — Authentication

JWT access + rotating refresh, server-enforced RBAC
Reason
Stateless access tokens suit a multi-frontend system; a revocable refresh token addresses the classic JWT weakness (can't invalidate a stolen long-lived token).
Alternatives
Server-side sessions — workable, but adds session-store infra for no benefit at this scale.

ADR-05 — Offline storage

IndexedDB via Dexie.js, not raw IndexedDB
Reason
Same browser guarantees, dramatically less hand-rolled boilerplate and fewer subtle bugs in a project already carrying significant scope.
Alternatives
SQLite via WASM (sql.js/absurd-sql) — more powerful but heavier and unnecessary for outbox-style storage; raw IndexedDB — rejected for maintainability, not capability.

ADR-06 — Synchronization strategy

Client-UUID idempotency + per-record batch outcomes
Reason
Directly and cheaply solves duplicate-submission and partial-batch-failure, the two scenarios the brief is most worried about.
Alternatives
Server-generated IDs with client-side dedup heuristics — rejected: heuristic matching is inherently less reliable than a guaranteed-unique client key.

ADR-07 — Inventory model

Append-only ledger + derived summary table
Reason
Auditable, race-safe via atomic increments, and directly answers "how do you know this number is right."
Alternatives
Single mutable counter (the brief's starting design) — rejected: exactly the pattern that causes the double-counting/negative-inventory failures the brief wants avoided.

ADR-08 — Buyer matching

Greedy rank-and-allocate, human-confirmed
Reason
Correctly scoped to the brief's own instruction to avoid unnecessary optimization complexity; a human confirms before commitment, bounding the algorithm's responsibility.
Alternatives
Constraint-solver/optimization approach — rejected as disproportionate to the problem size and explicitly discouraged by the brief.

ADR-09 — ML architecture

Offline batch job, scikit-learn, baseline always compared
Reason
Decouples model training from the request path; comparing against a naive baseline keeps model selection honest on a necessarily small dataset.
Alternatives
Inline/real-time inference — unnecessary, forecasts don't need sub-second freshness; deep learning — rejected, wrong tool for a small tabular dataset.

ADR-10 — Repository structure

Single monorepo: apps/, packages/, backend/, ml/, docs/
Reason
One place to review, one CI pipeline, atomic cross-cutting commits (e.g., a schema change and its matching TypeScript type in the same PR).
Alternatives
Per-service repos — rejected for the same reasons as ADR-01.

ADR-11 — Deployment approach

Free-tier managed hosts, no container orchestration
Reason
Matches the brief's instruction to avoid paid services and keeps operational complexity proportional to a project with one maintainer.
Alternatives
Kubernetes/self-managed VM cluster — rejected as disproportionate infrastructure for this project's scale and audience.
§25

Contradictions & Missing Requirements

1 — Scope vs. timeline (the big one) · Resolved

The brief asks for four production-grade interfaces, an offline sync engine, a matching system, and an ML pipeline. The real build window turned out to be two weeks total (one for development, one for testing) — far tighter than this document originally assumed. Decision: build only what §22's must-have list now contains — offline-safe collection recording and the inventory ledger, plus the minimum surrounding it needs to run — and defer everything else, including the buyer portal, public site, and predictions, as documented future work rather than partial, untested implementations.

2 — Payment settlement is unspecified · Resolved

The brief includes payment_method and reference_number fields, which in a Kenyan context strongly implies M-Pesa. Decision: the company pays suppliers by M-Pesa or cash; TAKAFLOW records which method was used and a reference for it. No live Safaricom Daraja disbursement integration — that's meaningfully larger scope (sandbox credentials, a registered till/paybill, callback handling) than this timeline supports, and is flagged as future work.

3 — Field-agent vs. fixed-branch collection is unstated · Resolved

Decision: confirmed — collection happens at physical branches with intermittent connectivity, not via roaming field agents on personal phones. The §10 offline design (Dexie/IndexedDB, desktop/tablet storage-quota assumptions) stands as designed; no revisiting needed.

4 — Quality/grade requirements have no data model · Resolved

Decision: staff record the grade/quality of the material at the same time they log the collection. A grade field on collection_transaction (§8) captures this; with the buyer portal deferred (item 1), it's stored for now and doesn't yet feed a matching constraint.

5 — "Collectors do not need accounts" vs. "design for future accounts" · Superseded by item 7

The original brief implied supplier accounts might come later, which is why supplier.user_id was made nullable. Item 7 below goes further: there's no supplier entity at all for this build. If self-service accounts are ever worth adding — only if the project continues past presentation — that reintroduces the entity as a migration, not a redesign.

6 — New: the real timeline breaks the original MVP, not just the roadmap

This document's roadmap (§21) and original MVP list (§22) were sized for a normal final-year-project runway. Learning the actual window is 2 weeks total is itself a contradiction against that sizing — even the "must-have" list as first written (4 interfaces, full RBAC, offline sync, a ledger, matching, and forecasting) is not buildable and testable by one person in a single dev week. §21 and §22 have been revised in place to reflect this: only Phases 1–8 are targeted, and the must-have list is cut to the offline-recording-and-ledger core plus its minimum supporting pieces.

7 — Resolved: no supplier registration exists

Clarified: collectors are not registered at all. Anyone — including someone with no phone or national ID — can bring material, have it examined and graded by staff, and be paid on the spot; there is no account, no search, and no requirement to recognize the same person across visits. This removes the identifier-uniqueness problem a registered-supplier model would have created for ID-less walk-ins, and it simplifies §8/§9: no supplier entity, just optional collector_name/collector_phone fields on collection_transaction kept for the payment record only.

8 — Resolved: predictive analytics dropped from this build

§13 requires roughly 12 weeks of real collection history before a regression model is even attempted, and returns "insufficient data" below that. A 2-week build cannot generate that history, so forecasting could only ever demo on seeded data — which is the "not practical" feeling that prompted this discussion in the first place. Decision: predictive analytics is fully out of scope for this build (moved from must-have to future scope in §22). The time it would have taken is spent instead on hardening and demonstrating the offline-sync/ledger correctness story — the actual technical core per §01 — with a simple, non-ML, ledger-derived low-stock flag as an optional bonus if time remains.

§26

Final Recommended Architecture

For the actual 2-week build: one FastAPI backend, one PostgreSQL database with an event-sourced inventory ledger at its core, and one authenticated PWA where branch staff record walk-in collections — offline-first via Dexie/IndexedDB, idempotent by construction through client-generated UUIDs, never silently losing or duplicating data. Inventory correctness is guaranteed by atomic ledger writes and database constraints, not application-level discipline alone. A thin admin view reads that same real data. Everything else this document designs — the buyer portal, public site, matching, and predictive analytics — is documented in full because a real architecture has to account for where the system grows next, but none of it is built now, and none of it is what the defense should hinge on.

The case for this being a CS project rather than a business plan rests entirely on the offline-sync-and-ledger correctness problem in §10–§11: a non-technical team can specify "record collections and track inventory," but idempotent sync, conflict handling, and concurrency-safe accounting are the parts that are actually hard to get right, and the parts worth defending. The technology stack proposed in the brief is adopted almost unchanged; the real engineering work in this document is in the data model (§08, §11) and in drawing an honest, defendable line between what two weeks can actually build and what stays future scope (§22).

Recommended next step: build and test Phases 1–8 from §21 to the standard §19 describes for offline/inventory scenarios specifically — that test coverage, demonstrated live, is the strongest evidence this is more than a business idea.
